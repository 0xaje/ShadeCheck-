# Submission review against the supplied judging criteria

This is a self-review of inspectable evidence, not an organizer score, prize prediction, or independent security audit.

| Criterion | Evidence a judge can inspect | Remaining boundary |
| --- | --- | --- |
| Privacy | Per-run keyed session identifiers; omitted arbitrary broadcast response text; private local artifacts; explicit public-export consent; documented observer and rule applicability | Traces deliberately retain sensitive correlations. Passing selected tests cannot establish anonymity. Historical artifacts retain their original bytes. |
| Usefulness | CLI, JSON/HTML reports, baseline comparisons, strict exit codes, consumer Action, prerequisite doctor and local runner | One independent wallet integration does not establish adoption across wallet teams. Each new integration still needs an adapter/workflow and relevant requirements. |
| Execution | Real five-family acceptance, exact negative exit assertions, downloaded/revalidated evidence, installed-wheel and browser checks | The frozen regression backend and current-client gate are different workflows; their coverage cannot be combined into a fictional single-client audit. |
| Originality | Inspectable ShadeCheck observer, deterministic rules, evidence/reporting and CI integration; clear upstream attribution | Originality and build-window eligibility are judged by the organizers. Dependency integration is not a new cryptographic protocol. |

## What still deserves engineering work after this submission

- Independently maintained integrations used by actual wallet/SDK teams in their release pipelines.
- Evaluation of legitimate workflows and false positives before recommending default strict policies broadly.
- More wallet, backend and supported-platform combinations, tested as separate matrices with explicit coverage.
- Default production privacy transports tested under their own relevant observer models. Explicit local test-mode findings are not a production wallet vulnerability claim.

These are real limits. They do not require inventing a token, integrating every listed resource, building a new wallet, or adding arbitrary network scanning. The submitted track is Core & Tooling; check eligibility against the organizer's actual rules rather than assumed requirements.
