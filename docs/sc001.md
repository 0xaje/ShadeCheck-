# SC-001 — Sync Pattern Disclosure

SC-001 tests observed block-range boundaries and inclusive request sizes against an explicit developer policy. It does not infer wallet birthday, transaction history, balance, or identity.

## Declared policy

The configuration format is:

```json
{
  "schema_version": 1,
  "sync": {
    "chunk_size": 20,
    "alignment_height": 0
  }
}
```

This example declares that each measured GetBlockRange request must start at a multiple of 20 and request exactly 20 blocks, inclusive. A different alignment_height shifts the origin. This is a developer-selected test requirement, not a universal Zcash rule or prescribed privacy guarantee. Selecting SC-001 without a valid policy configuration returns an error.

A MEDIUM finding occurs if an actual upstream request starts before or outside an aligned boundary, or requests a size different from the configured chunk. Findings embed the request and its actual delivered-block events, the exact policy, requested size, and violations. The observer records actual request time and transport session. These observations can depend on local synchronization state, but that relationship is not proven from a request alone.

Complete delivery of every requested height is required for PASS coverage. No request, fixture-only requests, or incomplete delivery cannot yield PASS. A violating request is visible even if its delivery is incomplete; it can therefore still fail the configured policy.

## Actual backend comparison

From the Windows repository, with Docker Desktop running:

```powershell
git pull --ff-only
.\.venv\Scripts\python.exe -m pip install .
.\.venv\Scripts\python.exe scripts/regtest.py up
.\.venv\Scripts\python.exe scripts/sync_pattern.py
```

The script chooses the last completed non-genesis 20-block chunk available from the actual local node and lightwalletd. It executes two fresh protocol-authentic client traces through the real ShadeCheck proxy:

| Behavior | Expected SC-001 result | Strict CLI exit |
| --- | --- | --- |
| Seven blocks starting three heights into the chunk | MEDIUM / FAIL | 1 |
| All 20 blocks from the aligned starting height | PASS for this declared policy | 0 |

Every delivered height and block hash is independently checked against the canonical regtest node. No transaction construction is needed: the actual chain blocks already exist. The comparison creates no fabricated blocks, successful RPC responses, or evidence.

The orchestration exits 0 only after verifying both actual outcomes. Inspect events.jsonl, backend-proof.json, report.json, and report.html for each trace, plus policy.json and comparison.json in the unique out/sync-pattern run directory.

To evaluate saved evidence:

```powershell
.\.venv\Scripts\shadecheck.exe test --events <events.jsonl> --rules SC-001 --config <policy.json> --policy strict
.\.venv\Scripts\shadecheck.exe explain SC-001
```

Select multiple implemented rules with --rules SC-001 SC-002 SC-003. Each selected rule must have coverage for an overall PASS. The default remains SC-002 for compatibility.

## Limits

- The client executes authentic RPCs but is not a full wallet sync algorithm.
- Only range alignment and request size are implemented in this family. Timing fingerprinting and repeated-history analysis remain outside coverage.
- The demonstration uses a historical completed chunk. Live chain-tip truncation, reorgs, and wallet resume strategy need explicit policy treatment and further integration.
- Padding requests increases bandwidth and may introduce other recognizable patterns. It does not establish anonymity.
- PASS means no violation of the configured SC-001 test was observed in the executed trace.
