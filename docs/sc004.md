# SC-004 — Transparent Fallback

SC-004 evaluates a native wallet payment path against an explicit requirement to remain shielded. The current integration tests explicit transparent recipient selection, not automatic Unified Address receiver fallback.

## Declared policy and evidence

```json
{
  "schema_version": 1,
  "payment": {"require_shielded": true}
}
```

Selecting SC-004 requires this policy. The local adapter records actual receiver validation, z_sendmany parameters, and terminal native-wallet operation results. It records transaction component counts from the actual node decoder and binds that receipt to submitted bytes with a SHA-256 payload fingerprint. The proxy independently records SendTransaction and the backend's response.

Native-wallet events have mode `wallet-adapter`; proxied RPC events have mode `upstream`. Adapter receipts depend on the trusted local test driver and node RPC. They are not facts inferred by a passive network observer. No spending keys are included in evidence; the developer-owned local regtest wallet volume holds its test keys.

| Observation under the shielded requirement | Result |
| --- | --- |
| Validated transparent recipient selected with a policy permitting recipient disclosure | MEDIUM |
| Decoded transaction contains transparent inputs or outputs, and its exact payload receives upstream acceptance | HIGH |
| Every measured attempt has an accepted shielded transaction or an observed FullPrivacy rejection of a transparent recipient for privacy error -8 | Covered; no finding if no disclosure is observed |
| Missing outcomes or an unrelated wallet error | WARN: incomplete coverage |

The rule does not treat a policy name alone as proof of shielding. Accepted transparent components still produce HIGH even if the request says FullPrivacy. The real comparison also independently verifies matching mempool bytes and node acceptance. Findings embed the native request, actual result, transaction receipt, and accepted broadcast events.

## Run on Windows

With Docker Desktop running, from the repository:

```powershell
git pull --ff-only
.\.venv\Scripts\python.exe -m pip install .
.\.venv\Scripts\python.exe scripts/regtest.py up
.\.venv\Scripts\python.exe scripts/transparent_fallback.py
```

The driver constructs real shielded setup payments to fund the isolated native wallet. Setup transfers are distinct from measured payments. Each measured payment is first constructed and locally accepted on that wallet node; its first submission to the separate verifier passes through ShadeCheck.

The permissive case sends Sapling funds to a validated transparent recipient with AllowRevealedRecipients. The hardened case attempts the same recipient with FullPrivacy, requires a real privacy rejection, then submits a real Sapling-to-Sapling payment with FullPrivacy.

| Measured case | Required result | Strict CLI exit |
| --- | --- | --- |
| Permissive Sapling-to-transparent payment | HIGH / FAIL | 1 |
| FullPrivacy rejection followed by accepted shielded payment | PASS for SC-004 | 0 |

The orchestration exits 0 only after checking both results. Inspect the unique out/transparent-fallback directory: each case contains events.jsonl, backend-proof.json, report.json, and report.html. The run also saves policy.json and comparison.json. Backend proof includes actual decoded transactions and independent verifier checks; evidence hashes can be inspected and recomputed.

Evaluate a saved trace with:

```powershell
.\.venv\Scripts\shadecheck.exe test --events <events.jsonl> --rules SC-004 --config <policy.json> --policy strict
.\.venv\Scripts\shadecheck.exe explain SC-004
```

## Limits

- This adapter covers the tested local zcashd wallet and explicit transparent recipient path. Arbitrary wallets, automatic Unified Address fallback, and receiver-selection libraries need their own instrumented integrations.
- The transaction structure receipt comes from trusted local node decoding. ShadeCheck does not independently implement a consensus transaction decoder.
- No claim is made that a failed payment exposed funds on chain. MEDIUM reports permissive selection; HIGH additionally requires accepted transaction bytes with transparent components.
- The observer still sees broadcast bytes for shielded payments. An SC-004 PASS does not resolve SC-002 broadcast linkability.
- PASS means no violation of this defined rule was observed in the executed flow. It does not establish anonymity.
